# Windows 并发通信压力复验（2026-10-17）

接续 [12 小时持续运行与剩余验收](windows-remaining.md)，本轮在同一台 `AgentDock-CleanWin11-20261016`（Windows 11 Pro 25H2、4 vCPU、固定 6 GiB、普通用户 DockTest）定位并复验最后的通信压力问题。使用独立合成项目和 VM 已保存的凭据，不导出凭据。原始证据位于 `artifacts/validation/windows-pressure-20261017/`，不入 Git。

**最终结论：本次 Windows 并发通信压力补测通过。修复版完整候选完成十轮、50 个真实任务；797 次严格辅助查询、416 次实际 MCP 任务调用及 312 次桌面心跳均无失败，执行中停止和三次客户端重连通过。已核对 VM 原件哈希与结束后的应用事件。此前十二小时结果属于旧候选，本次修复版未重跑十二小时。**

## 验收口径

- 每轮运行真实 Codex app-server → 安装版 MCP → Host → OpenCode Go 五角色任务，先 explorer，再并发 default、worker、reviewer、verifier；核验实际输出、角色写权限、用量及重复请求身份。
- 连续十轮；只读辅助查询保持原设置：连接 1,200 ms、读取 6,000 ms、每次完成后间隔 650 ms。任何失败都保留并使该项失败，没有放宽阈值。
- 产品调用实际连接预算为 3,000 ms、响应预算为 55,000 ms；辅助查询超时、真正 MCP 调用失败、模型任务超过探针 180 秒等待上限分别统计。产品任务超时仍为 1,200 秒。
- 同时采样资源和桌面窗口 500 ms WM_NULL 心跳；结束后验证真实执行中停止、三次新 MCP 客户端重连、原 Host 身份、无未完成任务和执行进程残留。

## 复现与根因

11:00–11:02 的 1/2/4 并发梯度完成七个任务，119 次严格查询无失败；四并发启动时 CPU 达 100%、可用内存降至 373 MiB，出现一次约 2.4 秒的客户端准备/写入阶段延迟。该资源相关性不能单独证明根因。

旧候选 `.20261016.3` 的正式复现于 11:03:17–11:12:37 运行：前七轮五角色通过，第八轮超过探针每任务 180 秒的等待上限后停止。辅助查询 639 次成功、19 次失败，最长约 13,553 ms，通信压力仍失败。325 次真正 MCP 调用均返回成功；该次任务等待超限不写成产品 1,200 秒任务超时，任务完成也不覆盖严格通信失败。

为区分锁、持久化、GC 和线程池，使用独立诊断构建，以专用写线程记录匿名阶段耗时和运行时计数，不修改正式产品的日志路径。旧实现的两轮诊断中，十个任务全部完成，但严格查询有两次读取超时（约 6.3/6.6 秒）。失败窗口中共享线程池只有 12 个工作线程，待执行队列从 2 增到 15，完成计数约 2.4 秒不增长；GC 累计暂停保持约 5 ms，非 wait 业务段最长约 17 ms，持久化 Flush 最长约 72 ms。这组证据指向阻塞工作占用线程池，而非这些业务段或 GC 的长暂停。

`OpenCodeEngine.ExecuteAsync` 原来把同步 stdin 写入、stdout 读取、stderr 读取和 `WaitForExit(-1)` 放进 `Task.Run`。四并发时这些长时间阻塞操作占用共享线程池，挤压 Host 管道处理及模型中继的异步后续工作。修复将这四类阻塞工作改为 `Task.Factory.StartNew` 配合 `LongRunning | DenyChildAttach` 和 `TaskScheduler.Default`，其余取消、等待、异常和进程释放顺序不变。线程生命周期仍随任务结束释放，不增加模型并发数。机制参考 [Microsoft 的线程池饥饿诊断](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-threadpool-starvation)。

同样诊断采集下的修复构建于 11:16:53–11:18:03 完成两轮十个任务：91 次严格查询、零失败，观察到四并发。处理器调度最大等待由约 614 ms 降为 0.364 ms；新构建的持久化最长 Flush 反而约 170 ms，不能把改进解释为写盘变快。两轮对照只能作为根因验证，正式十轮仍单独判定。

证据：`guest-evidence/gradient-*.json*`、根目录的 `stress-*.json*`、`diagnostic-1/` 和 `diagnostic-2/`；诊断源码、构建和原实现副本均留在本轮 artifacts，不进入正式包。

## 回归与独立复核

新增 `BlockingIoSchedulingTests` 在隔离子进程内限制最多八个共享工作线程，通过四个真实 `ExecuteAsync` 调用和可控阻塞进程模拟器占满执行路径，再要求排入共享线程池的心跳在两秒内执行。不改 xUnit 主进程的线程池设置，不调用真实模型。

旧实现心跳两秒超时，子进程退出码 2；修复后通过，收紧“至少八条阻塞调用已进入”的前置断言后再次通过，测试约 186 ms。此前一次受限执行环境中的 VSTest 连接超时属于测试宿主启动失败，保留记录但不当作产品红测。

本轮共 **121 项不同的 Windows 测试通过，19 项仅适用 macOS 的用例跳过**：Engine 全套 85 项，加显式启用的五项真实沙箱；Core/Host 全套 30 项，加显式启用的管理管道权限测试。重复的单项回归不重复计数。证据在 `tests/` 中的 `engine-full.trx`、`sandbox-enabled.trx`、`core-host-full.trx`、`host-restricted-enabled.trx` 和 `blocking-io-{before-runtime,after,final}.trx`。

DeepSeek 只读复核已完成，未报告产品功能缺陷，指出饱和断言过弱；已收紧并重跑。报告 `independent-review.md` 保留复核边界：Mac 只有静态审查，没有把 Windows 通过等同于 Mac 实测。
